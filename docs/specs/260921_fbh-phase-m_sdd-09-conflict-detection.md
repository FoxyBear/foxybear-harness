# SDD-09: Phase M-5 — Conflict Detection (Deferred to post-M-6, conditional activation)

**Date:** 2026-09-21 (revised 2026-09-22 per council deferral)
**Project:** FoxyBear Harness Phase M (`development/foxybear`)
**Status:** Draft (technical content re-audit passed; deferral + activation gate + abort A8 added per council, pending human gate)
**Master:** `260921_fbh-phase-m_sdd-00-master.md`
**Depends on:** SDD-08 (M-6 verification — produces the contradiction-rate evidence M-5 consumes to decide whether to activate; the activation threshold is defined in sdd-08 and referenced here), SDD-05 (M-2 auto-capture — `ActionNode`/`ErrorNode`/hyperedges for path localization, extraction LLM client reused for `llm_verify`), SDD-03 (M-1 hypergraph schema — `node`/`hyperedge`/`event` tables, bi-temporal `BaseNode` with `invalidated_by` + `prev_version_id`, `INVALIDATE` event_type).
**Owns:** SC-5 `ConflictDetector` service interface (`check(content, project_id) → ADD/UPDATE/DELETE`), SC-6 `memory.conflict` config, SC-7 M-5 spike (FP rate), the save-time decision-driven write loop, bi-temporal soft-delete emission on DELETE, cross-project isolation at store time, the M-5 activation gate (council deferral to post-M-6).

Implements Phase M-5: save-time conflict detection wired into `Memory.store`. When a new memory is stored, `ConflictDetector.check` finds graph neighbors in the same `project_id` (MOSAIC-style save-time cross-reference), scores contradiction by cosine similarity against the new content's embedding, and on contradiction triggers HiGram-style path localization to identify the minimal subgraph that supports the old memory. The decision-driven write loop returns one of `ADD` (no contradiction — store new normally), `UPDATE` (cosine < `cosine_threshold` — coordinated rewrite of the old memory, new version linked via `prev_version_id`), or `DELETE` (cosine very low, e.g. < `delete_threshold` (default 0.1) — bi-temporal soft-delete of the old memory via `tx_to = now`, `status = DELETED`, `invalidated_by = new_id`, `INVALIDATE` event emitted). The existing `cosine > 0.95` dedup (memory.ts:302-345) stays unchanged and runs after conflict detection — dedup merges near-duplicates, conflict detection handles contradictions.

**Council deferral (2026-09-22):** M-5 is deferred to post-M-6. Building conflict detection before measuring whether contradictions occur is "infrastructure for an unmeasured problem." M-6 (sdd-08) produces the contradiction-rate evidence M-5 consumes to decide whether to activate. The sdd-09 `implement` stage SHALL NOT proceed until sdd-08's `tests` stage has passed AND sdd-08 has measured a contradiction rate at or above the activation threshold (threshold defined in sdd-08, referenced here). If the contradiction rate is below threshold, M-5 remains deferred. If no contradiction evidence is produced after 2 weeks of production telemetry, abort A8 fires and M-5 is deferred indefinitely (per master SC-11).

### Wiring (CC-2 dormant code wired, not rewritten)

1. **WHEN** `Memory.store` is invoked (memory.ts:629 public facade, memory.ts:585 `Effect.fn("Memory.store")`, memory.ts:253 `storeImpl`), the system **SHALL** invoke `ConflictDetector.check(content, project_id)` after the embedding is computed (memory.ts:263 `getEmbedding`) and before backend dispatch (memory.ts:266 `getGlobalMemoryBackend`) — so the check covers both the SurrealBackend path (memory.ts:266-294) and the legacy SQLite path (memory.ts:296-377).

2. **WHEN** `ConflictDetector.check` returns verdict `ADD`, the system **SHALL** proceed with the existing `storeImpl` flow (SurrealBackend dispatch or SQLite path, including the existing `cosine > 0.95` dedup merge at memory.ts:310-344). The dedup check is NOT bypassed.

3. **WHEN** `ConflictDetector.check` returns verdict `UPDATE` with `target = old_node_id`, the system **SHALL** invoke the rewrite path: store the new content as a new node (new `node_id`), set `prev_version_id = old.node_id` and `version = old.version + 1` on the new node, close the old node's `tx_to = now` (preserving it as a historical version), and emit an `UPDATE` event to the `event` table. The system **SHALL NOT** call the existing dedup path for UPDATE verdicts.

4. **WHEN** `ConflictDetector.check` returns verdict `DELETE` with `target = old_node_id`, the system **SHALL** invoke the retract path: store the new content as a new node, then bi-temporal soft-delete the old node (set `tx_to = now`, `status = DELETED`, `invalidated_by = new.node_id`), emit an `INVALIDATE` event (event_type=`INVALIDATE`, target_id=old.node_id, target_type=node) to the `event` table. The system **SHALL NOT** call the existing dedup path for DELETE verdicts. The system **SHALL NOT** hard-delete the old node — hard-deletes are GC-only on `status = ARCHIVED` past retention (CC-7).

### Neighbor lookup (MOSAIC-style save-time cross-reference)

5. **WHEN** `ConflictDetector.check(content, project_id)` is invoked, the system **SHALL** compute the embedding of `content` (reusing `Embedding.embedSafe` via memory.ts:238 `getEmbedding`) and query existing live nodes (per SC-2 `is_live(now)`) of type `MEMORY` in the same `project_id` with cosine similarity to the new embedding, ranked descending. The query pattern **SHALL** reuse the SurrealBackend hybrid retrieval semantic leg (surreal-backend.ts:217-225 — `vector::similarity::cosine` against the `node` table, scoped by `project_id`).

6. **WHEN** neighbor lookup returns zero live `MEMORY` nodes in the same `project_id`, the system **SHALL** return verdict `ADD` with no `target`. No further scoring, localization, or rewrite is performed.

7. **WHEN** neighbor lookup returns one or more live `MEMORY` nodes, the system **SHALL** take the top neighbor (highest cosine) as the candidate and proceed to contradiction scoring. The system **SHALL NOT** consider neighbors from other `project_id`s (see Cross-project isolation, reqs 22-24).

### Contradiction scoring

8. **WHEN** a candidate neighbor is identified, the system **SHALL** compare its cosine similarity to the new content's embedding against `memory.conflict.cosine_threshold` (default 0.3, per SC-6). The cosine computation **SHALL** reuse `cosineSimilarity` from memory.ts:73.

9. **WHEN** the candidate's cosine similarity is `>= cosine_threshold` (default 0.3), the system **SHALL** return verdict `ADD` — the new content is not a contradiction, it's a complement or near-duplicate, and falls through to the existing `cosine > 0.95` dedup path in `storeImpl`.

10. **WHEN** the candidate's cosine similarity is `< cosine_threshold` (default 0.3) and `>= memory.conflict.delete_threshold` (default 0.1, per SC-6 — consumed from config, NOT hardcoded; semantically distinct from `memory.decay.archived_threshold`, see req 27), the system **SHALL** return verdict `UPDATE` with `target = candidate.node_id` — the new content contradicts the old, but both are about the same topic; the old needs rewriting, not deletion.

11. **WHEN** the candidate's cosine similarity is `< memory.conflict.delete_threshold` (default 0.1), the system **SHALL** return verdict `DELETE` with `target = candidate.node_id` — the new content so strongly contradicts the old that the old is wrong, not just stale. The old is soft-deleted.

12. **WHEN** `memory.conflict.llm_verify` is `true` (set by the M-5 spike fallback), the system **SHALL** invoke an LLM verification step between req 10/11's threshold classification and the verdict return: pass the new content and the candidate's content to the configured extraction LLM (per SDD-05's `memory.extraction.model`) with a binary prompt ("Does the new content contradict the old? yes/no"). The LLM's verdict **SHALL** override the cosine-based verdict only toward `ADD` (LLM says "no contradiction" → `ADD` regardless of cosine). The LLM **SHALL NOT** override toward `UPDATE` or `DELETE` (cosine remains the authority for those). When `llm_verify` is `false` (default, pre-spike), this step is skipped.

    **WHEN** `memory.conflict.llm_verify` is `true` but the LLM verification call cannot complete (network error, rate limit, malformed response) OR SDD-05's extraction LLM client is unavailable (missing provider keys, SDD-05 spike fell back to regex-only with no LLM client wired, model endpoint unreachable), the system **SHALL** fall back to verdict `ADD` (no destructive `UPDATE` or `DELETE` without verification — the operator opted into LLM verification, so cosine alone is not trusted to take destructive action), log a warning ("conflict: llm_verify requested but LLM unavailable, defaulting to ADD"), and proceed with the `ADD` path (req 16). The store call **SHALL NOT** crash on an LLM-unavailable condition. This fallback ensures that a transient LLM outage does not corrupt the graph by triggering destructive verdicts on unverified cosine scores, at the cost of a duplicate `ADD` that a future store call (with LLM available) can reconcile.

### Path localization (HiGram-style)

13. **WHEN** the verdict is `UPDATE` or `DELETE`, the system **SHALL** invoke `localize(target_id)` to identify the evidence path supporting the old memory: which hyperedges reference `target_id` (via `SurrealHypergraphBackend.queryHyperedges([target_id])` per SDD-03), which `ActionNode`/`ErrorNode`/`MessageNode` produced or referenced it (via the `COLLABORATION`/`EVIDENCE`/`ERROR_CORRECTION` hyperedges' `node_ids` arrays), and which other `MEMORY` nodes cite it as `source_nodes`.

14. **WHEN** `localize` returns a non-empty subgraph, the system **SHALL** record the subgraph node_ids and hyperedge_ids in the `UPDATE` or `INVALIDATE` event's `payload` field (per SC-9 `event.payload` is flex). The recorded subgraph is the audit trail proving which memories were affected by the contradiction. The system **SHALL NOT** rewrite or soft-delete the subgraph's other nodes in Phase M-5 — only the old memory itself is rewritten/retracted. Subgraph-wide coordinated rewrite is a fast-follow.

15. **WHEN** `localize` returns an empty subgraph (no hyperedges reference the old memory — it's an orphan), the system **SHALL** proceed with the UPDATE or DELETE verdict without modification. An orphan old memory is still a valid target for rewrite or retract.

### ADD decision

16. **WHEN** the verdict is `ADD`, the system **SHALL** return `{ verdict: "ADD" }` with no `target`. `storeImpl` proceeds to the existing flow (SurrealBackend `backend.write` at memory.ts:274 or SQLite insert at memory.ts:351-365), including the existing `cosine > 0.95` dedup merge for the SQLite path. The new memory is stored with `version = 1`, `prev_version_id = null`, `tx_from = now`, `tx_to = Infinity`, `status = ACTIVE`. A `STORE` event is emitted (per SC-9) — event emission for the ADD path is owned by SDD-03/SDD-05's `SurrealHypergraphBackend.store` and is not re-emitted by SDD-09.

### UPDATE decision (coordinated rewrite)

17. **WHEN** the verdict is `UPDATE` with `target = old.node_id`, the system **SHALL** store the new content as a new node (new `node_id`) with `node_type = MEMORY`, `version = old.version + 1`, `prev_version_id = old.node_id`, `valid_from = now`, `valid_to = Infinity`, `tx_from = now`, `tx_to = Infinity`, `status = ACTIVE`, `invalidated_by = null`.

18. **WHEN** the new node is stored, the system **SHALL** close the old node's bi-temporal window: set `old.tx_to = now` (the old is no longer the live version — the new version supersedes it). The old node's `status` stays `ACTIVE` (it's still a valid historical version, queryable via `tx_to > now` filters). The system **SHALL NOT** set `old.status = DELETED` on UPDATE — UPDATE preserves the old as historical, DELETE marks it deleted.

19. **WHEN** the UPDATE completes, the system **SHALL** emit an `UPDATE` event to the `event` table: `event_type = UPDATE`, `target_id = new.node_id`, `target_type = node`, `payload = { old_node_id, subgraph_node_ids, subgraph_hyperedge_ids }` (the subgraph from req 14's localization). The `Memory.store` return value **SHALL** be the new node's `MemoryEntry` (so the caller — `MemoryRememberTool` at tools.ts:13 — sees the new id).

### DELETE decision (bi-temporal soft-delete)

20. **WHEN** the verdict is `DELETE` with `target = old.node_id`, the system **SHALL** store the new content as a new node (same fields as UPDATE's new node, req 17, except `prev_version_id = null` — DELETE is not a version chain, it's a contradiction), then bi-temporal soft-delete the old node: set `old.tx_to = now`, `old.status = DELETED`, `old.invalidated_by = new.node_id`. The old node's `valid_to` is left unchanged (the old fact was believed true in the world until the new fact arrived — `valid_to` closes only if the fact itself ended, which is a separate concern).

21. **WHEN** the DELETE completes, the system **SHALL** emit an `INVALIDATE` event to the `event` table: `event_type = INVALIDATE`, `target_id = old.node_id`, `target_type = node`, `payload = { new_node_id, subgraph_node_ids, subgraph_hyperedge_ids }`. The `Memory.store` return value **SHALL** be the new node's `MemoryEntry`. The system **SHALL NOT** emit a `DELETE` event — `DELETE` event_type (per SC-9) is reserved for hard-deletes (GC); soft-deletes emit `INVALIDATE`.

### Cross-project isolation (Security)

22. **WHEN** `ConflictDetector.check(content, project_id)` is invoked with a non-empty `project_id`, the system **SHALL** scope neighbor lookup (req 5) to live `MEMORY` nodes where `attributes.project_id == project_id` OR `attributes.project_id == "global"` (global memories are shared across projects, per the existing scope semantics in surreal-backend.ts:208-212 — `project_id = "${pid}" OR project_id = "global" OR project_id = ""`). The system **SHALL NOT** return neighbors from a different non-global `project_id`.

23. **WHEN** `ConflictDetector.check` is invoked with `project_id` undefined or empty, the system **SHALL** scope neighbor lookup to live `MEMORY` nodes where `attributes.project_id == "global"` OR `attributes.project_id` is empty. The system **SHALL NOT** return neighbors from any project-scoped memory.

24. **WHEN** a neighbor lookup query returns a node whose `attributes.project_id` does not match the request's `project_id` (and is not `"global"` or empty), the system **SHALL** treat it as a data-isolation bug: log a warning with both project_ids, exclude the node from the candidate set, and continue. The system **SHALL NOT** crash the store call on an isolation violation — the new memory is still stored (verdict `ADD` if no valid candidates remain).

### Spike (SC-7 M-5, CC-3)

25. **WHEN** the SDD-09 spec reaches the `tests` stage, the spec's acceptance tests **SHALL** include a spike test (throwaway, not production code) that: loads 100 real session turns from the existing session transcript fixtures, runs `ConflictDetector.check` against each turn's content with `cosine_threshold = 0.3` and `llm_verify = false`, manual-labels each verdict as true-positive (real contradiction) or false-positive (cosine flagged a contradiction that a human judge disagrees with), and computes `FP_rate = false_positives / total_contradictions`.

26. **WHEN** the spike test's `FP_rate < 10%`, the spike **SHALL** pass and the implementation **SHALL** proceed with `cosine_threshold = 0.3` and `llm_verify = false` as defaults. **WHEN** the spike test's `FP_rate >= 10%`, the spike **SHALL** fail and the spec's HOW **SHALL** be revised to the fallback: raise `cosine_threshold` to 0.2 (more conservative — fewer contradictions flagged) AND, **IF** SDD-05's extraction LLM client is available (SDD-05 spike passed, OR SDD-05 fell back to regex-only but the LLM client remains wired for `llm_verify` per seam 4), set `llm_verify = true` (LLM verification overrides false-positive contradictions toward `ADD`). **IF** SDD-05's LLM client is unavailable (missing provider keys, model endpoint unreachable), the degraded fallback is `cosine_threshold = 0.2` only — `llm_verify` stays `false`, because setting `llm_verify = true` with no LLM available would always fall back to `ADD` per req 12 and mask real contradictions. The revised defaults **SHALL** be reflected in SC-6's `memory.conflict` config before `implement` proceeds. The degraded fallback (`cosine_threshold = 0.2`, `llm_verify = false`) **SHALL** be documented in SC-6 as an allowed configuration when the LLM client is unavailable.

### Config (SC-6, CC-6)

27. **WHEN** the system reads `memory.conflict` from `~/.config/foxybear/fbh.json`, the system **SHALL** consume `cosine_threshold` (default 0.3, range 0.0-1.0) as the ADD/UPDATE contradiction threshold (req 10), `delete_threshold` (default 0.1, range 0.0-1.0) as the UPDATE/DELETE strong-contradiction threshold (req 11), and `llm_verify` (default `false`) as the LLM verification toggle (req 12). `delete_threshold` is semantically distinct from `memory.decay.archived_threshold` (default 0.1, per SC-3) — `archived_threshold` gates the DEPRECATED→ARCHIVED lifecycle transition on a confidence score (SC-3 line 178), while `delete_threshold` gates the UPDATE→DELETE conflict verdict on a cosine similarity score (reqs 10-11); they share a default value but represent different concepts (lifecycle confidence vs. conflict cosine), so a separate key is cleaner than reusing `archived_threshold`. The config **SHALL** be added to the zod schema at config/foxybear.ts:4-73 as a new `conflict` sub-object alongside the existing `dedup_threshold` (config/foxybear.ts:25) and `consolidation` (config/foxybear.ts:31-38) sub-objects. The master SC-6 `memory.conflict` config (master line 287-290) **SHALL** be updated to include `delete_threshold` alongside `cosine_threshold` and `llm_verify` — the master spec is the canonical config shape, and the addition propagates to all feature specs that consume it (cross-reference: master SC-6 update required before `implement` proceeds).

28. **WHEN** `memory.conflict.cosine_threshold` is changed from 0.3 to 0.2 in `fbh.json`, the system **SHALL** flag fewer contradictions (only cosine < 0.2 triggers UPDATE/DELETE). **WHEN** `memory.conflict.delete_threshold` is changed from 0.1 to 0.05 in `fbh.json`, the system **SHALL** flag fewer `DELETE` verdicts (only cosine < 0.05 triggers `DELETE`; cosine in [0.05, 0.3) now triggers `UPDATE` instead of `DELETE`). **WHEN** `memory.conflict.llm_verify` is changed from `false` to `true`, the system **SHALL** invoke the LLM verification step (req 12). Config consumed **SHALL** be proven by a test that changes each value and asserts the behavior changes (CC-6).

### Seams noticed (audit-relevant)

1. **The existing `cosine > 0.95` dedup is ONLY in the legacy SQLite path** (memory.ts:302-345). The SurrealBackend dispatch (memory.ts:266-294) does NOT do dedup — it calls `backend.write` which inserts unconditionally. This means the master spec's statement "Wire into Memory.store (before the existing dedup check)" needs clarification: the dedup check exists only in the SQLite path. SDD-09 wires `ConflictDetector.check` at the top of `storeImpl` (after `getEmbedding`, before backend dispatch) so it runs for BOTH paths uniformly. The SQLite dedup at memory.ts:310-344 stays for `ADD` verdicts; the SurrealDB path has no dedup, which is a separate concern (SDD-03 may address). This is not a blocker — the wiring point is unambiguous.
2. **The bi-temporal `INVALIDATES` hyperedge vs `INVALIDATE` event** — the master spec (SC-2, SC-3) refers to "emit an `INVALIDATES` edge" but SC-4 lists only 7 hyperedge types and `INVALIDATES` is not among them. SC-9 lists `INVALIDATE` as an `event_type` in the `event` table. SDD-09 interprets "INVALIDATES edge" as the bi-temporal `invalidated_by` back-pointer field on the old node (per SC-2's `invalidated_by` field definition) PLUS the `INVALIDATE` event in the `event` table (per SC-9). No new hyperedge type is added. If the audit finds the master intended a new `INVALIDATES` hyperedge type, that's a SDD-03 dependency to add — SDD-09 emits the field + event either way.
3. **`UPDATE` semantics: same node_id with version++, or new node_id with prev_version_id back-pointer?** — SC-2 says "version: starts at 1, increments on UPDATE" AND "prev_version_id: prior version of this node". These are reconciled by interpreting UPDATE as: new node (new `node_id`) with `version = old.version + 1` and `prev_version_id = old.node_id`, old node's `tx_to` closed. The version chain is a singly-linked list of node_ids via `prev_version_id`, with `version` incrementing along the chain. This preserves bi-temporal history (the old node is queryable via `tx_to > now`) AND follows the version-chain semantics. The audit should confirm this matches SDD-03's `BaseNode` definition.
4. **`llm_verify` fallback depends on SDD-05's LLM extraction client** — req 12's LLM verification step reuses the extraction LLM (`memory.extraction.model`, default Qwen2.5-7B on DeepInfra per SC-6). Two failure modes are distinguished:
   (a) **SDD-05's spike falls back to regex-only, LLM client still wired** — regex replaces LLM for entity/hyperedge *extraction*, but the LLM client (Qwen2.5-7B on DeepInfra) remains reachable for `llm_verify`'s binary contradiction prompt (a different use-case of the same client). `llm_verify = true` works normally; req 12's override applies.
   (b) **LLM client unavailable** (missing provider keys, network failure, model endpoint down) — req 12's fallback applies: `check` returns `ADD` and logs a warning ("conflict: llm_verify requested but LLM unavailable, defaulting to ADD"). The store call does not crash.
   Req 26's spike fallback gates `llm_verify = true` on case (a) (LLM client still wired); if case (b) applies (client unavailable), the degraded fallback is `cosine_threshold = 0.2` only (no `llm_verify`), because calling `llm_verify = true` with no LLM would always fall back to `ADD` per req 12 and mask real contradictions. The audit should confirm SDD-05's LLM client is accessible from `ConflictDetector` via the shared config (`memory.extraction.model`).
5. **Activation gate is a process gate, not a runtime gate (council deferral).** G1-G4 govern when the sdd-09 spec is *allowed to proceed to `implement`*, not what `ConflictDetector` does at runtime. The `tools/sdd` workstream's stage-gate check enforces G1 (sdd-08 before sdd-09). The activation threshold value lives in sdd-08's spec (sdd-08 defines the contradiction-rate metric and the threshold); sdd-09 only references it. A future change to the threshold is a sdd-08 change, not a sdd-09 change. The 2-week production telemetry window for abort A8 is measured from sdd-08's `tests` completion timestamp, not from sdd-09's spec acceptance date — sdd-09 can sit deferred indefinitely without the clock starting; the clock starts when M-6 evidence begins accumulating.

### What is explicitly NOT built (out of scope for SDD-09)

- Subgraph-wide coordinated rewrite (HiGram's "jointly revises intra-unit memory and inter-unit dependencies") — SDD-09 localizes the subgraph (req 14) and records it in the event payload, but does not rewrite the subgraph's other nodes. That's a fast-follow.
- Conflict detection across non-MEMORY node (`ENTITY`, `PROCEDURE`, `INSIGHT`) — only `MEMORY` nodes are checked in Phase M-5. Entity-level contradiction is already handled by graduation.ts:73-83 (dormant, wired in SDD-02).
- LLM-driven contradiction classification (MemGraphRAG's multi-agent reconciliation) — out of scope; cosine + optional LLM verify (binary) is the M-5 mechanism.
- Conflict detection in the recall path — SDD-09 is save-time only. Recall-time conflict resolution is a fast-follow.
- M-5 activation before M-6 evidence exists — the activation gate (G1-G4) is a hard process gate. No `implement` work on sdd-09 (not even a tracer bullet) is permitted until sdd-08's `tests` has passed AND the contradiction-rate evidence is in the decision log. A tracer bullet for the wiring point (req 1) is permissible only inside sdd-03's or sdd-05's own tracers, not as a sdd-09 activity.
